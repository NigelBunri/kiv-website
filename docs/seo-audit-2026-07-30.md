## 3. What was implemented

### 3.1 Brand entity & Knowledge Graph (`components/StructuredData.tsx`)

`OrganizationJsonLd` expanded from 5 fields to the full set schema.org actually validates for an org of this kind: `name`, `alternateName`, `url`, `logo` (as an `ImageObject`, 512×512), `image`, `description`, `email`, `contactPoint`, `areaServed`, `knowsAbout`, `brand`, `publishingPrinciples`, `parentOrganization`. Given a stable `@id` (`.../#organization`) so `WebSiteJsonLd`, `ArticleJsonLd`, `WebPageJsonLd`, and `ProductJsonLd` can all reference the *same* entity instead of repeating inline copies — this is what lets Google merge signals from every page into one confident entity instead of treating each page's markup as a separate, weaker claim.

**Deliberately omitted, and why:** `founder`, `foundingDate`, `sameAs`. There is no founder name, founding date, or any live social/Wikipedia/Crunchbase profile URL anywhere in this codebase. Fabricating any of these would be exactly the kind of unverifiable structured-data claim Google's spam policies penalize with a manual action — and a broken `sameAs` link actively *hurts* Knowledge Graph confidence rather than helping it. **This is the single biggest lever this report could not pull** — see Section 9.

Also skipped: a `SearchAction`/sitelinks-searchbox (no search feature exists on the site to point it at) and `FAQPage` schema (Google restricted FAQ rich results to government/health sites only in August 2023 — adding it elsewhere produces no rich result, so it wasn't worth fabricating Q&A pairs out of prose support articles).

### 3.2 Logo in Google Search (favicon + rich results)

Generated a complete icon set from the real KIV logo (`public/images/kiv-logo.png`) via `sharp`, replacing the placeholder "KIV" monogram SVGs that were there before:

| File | Size | Purpose |
|---|---|---|
| `favicon.ico` | 16/32/48 multi-res | Legacy browser tab icon |
| `favicon-16.png` / `-32.png` / `-48.png` | exact | Modern browser tab icon |
| `apple-touch-icon.png` | 180×180 | iOS home screen |
| `android-chrome-192x192.png` / `-512x512.png` | exact, full-bleed | Android/PWA, `purpose: "any"` |
| `kiv-logo-maskable-192.png` / `-512.png` | exact, 60% safe-zone padding | Android/PWA, `purpose: "maskable"` (a *separate*, padded image — reusing the full-bleed one under `maskable` would get the crown clipped when Android applies a circular mask) |
| `mstile-150x150.png` + `browserconfig.xml` | 150×150 | legacy Windows tiles |
| `og-cover.png` | **1200×630** | Open Graph / Twitter card default |

The logo is now referenced consistently everywhere Google's Logo rich result and Merchant/Organization guidelines check: `<link rel="icon">` (multiple sizes), `apple-touch-icon`, `manifest.webmanifest`, `Organization.logo` (as a proper `ImageObject` with explicit width/height ≥ 512px, PNG, square, publicly reachable — verified 200 OK), and the Open Graph/Twitter image.

**Why the OG image changed:** it was previously the bare 512×512 square logo. Facebook/Twitter/LinkedIn "large image" cards want roughly a 1.91:1 landscape ratio — a square logo gets awkwardly cropped or padded in link previews. Composited the real logo onto a branded cream/gold 1200×630 canvas instead (`scripts` used once, not committed — a throwaway generation step, reproducible from `public/images/kiv-logo.png`).

Also added explicit `robots: { googleBot: { "max-image-preview": "large" } }` site-wide — this is the actual flag that makes a page *eligible* for Google to show a large image/logo in search results at all; without it, Google defaults to a small thumbnail regardless of how good the source image is.

### 3.3 Branded-term reinforcement (`app/layout.tsx`, `lib/metadata.ts`)

Every page's title template changed from `%s | KIV` to `%s | Kingdom Impact Ventures` — the full legal name, not the abbreviation, on every single indexed page title (checked title lengths across all 28 routes first; longest combination stays well under Google's ~60-char soft truncation guideline except two `/updates/` article titles, which is an acceptable tradeoff for site-wide consistency). This is the highest-value, lowest-risk lever available for reinforcing "Kingdom Impact Ventures" as *this site's* branded phrase across everything Google indexes.

### 3.4 Homepage entity clarity (`app/page.tsx`)

- Meta description rewritten to lead with the full name and state plainly what KIV does (148 chars, safely under the truncation limit) — was previously 88 characters and used the abbreviation.
- Added a new, plain-language "What Kingdom Impact Ventures is" section directly after the hero: two short paragraphs stating what the org is, who runs it (KCAN), and what it builds — grounded entirely in facts already present elsewhere in the codebase (KIS's existing "Christian digital ecosystem" description, the real KCAN full name, the real product slate). No invented positioning, no keyword list forced in — this is exactly the kind of clear, quotable definitional content that helps Google disambiguate a brand entity from generic dictionary-word queries like "Kingdom" or "Impact."

### 3.5 Structured data coverage (`app/about`, `app/contact`, `app/updates/[slug]`)

- `WebPageJsonLd` with `type="AboutPage"` / `type="ContactPage"` on those two routes (schema.org's real WebPage subtypes — not `PrivacyPolicy`/`TermsOfService`, which some checklists list but aren't valid schema.org types; using them would fail validation, so `/privacy` and `/terms` were deliberately left as-is rather than marked up with something invalid).
- `ArticleJsonLd` on `/updates/[slug]` — replaced a one-off inline JSON-LD block with the shared, `@id`-linked component.
- `ProductJsonLd` (all 5 products) now includes a real product `image` and references the Organization/WebSite via `@id` instead of duplicating inline objects. No `offers` or `aggregateRating` — there's no real price or review data, and fabricating either is the single most common cause of a manual structured-data spam action.

### 3.6 Internal linking (`components/SiteShell.tsx`, `components/PageBlocks.tsx`)

- **Footer rebuilt.** It previously linked *only* to the 11 legal/utility pages — never to primary nav (About, Mission, Products, Partners, Investors, Updates, Contact, Support, Download) or any of the 5 product pages. Every page on the site was one click away from the legal pages and zero clicks from a footer link to the actual products. Rebuilt into three labeled columns: Company, Products, Legal & trust.
- **New `Breadcrumbs` component** pairs a *visible* breadcrumb trail with the existing `BreadcrumbJsonLd` — previously the JSON-LD had no matching visible content anywhere on the site, which is both a weaker trust signal for Google (structured data is supposed to describe visible content) and a missed navigation aid for real visitors. Rolled out across all pages that had breadcrumb JSON-LD (skips rendering below 2 items, per the fix in Section 2).

### 3.7 Accessibility & performance — verified, not just assumed

Audited before assuming gaps: this codebase already had prior, documented WCAG-AA contrast work (`--ink-soft`, `--ink-faint`, `--gold-strong` all carry comments recording specific contrast-ratio fixes), `aria-expanded`/`aria-controls`/`aria-label`/`aria-current` on the nav, focus-visible outlines, self-hosted fonts via `next/font` (eliminates the render-blocking Google Fonts request entirely), and an existing responsive-image system (`ResponsiveImage`) with mandatory `alt`, explicit `width`/`height` (zero layout shift — confirmed CLS: 0 in Lighthouse), and `loading="lazy"` below the fold. The one real gap found (breadcrumb contrast) is fixed in Section 2.

## 8. What still needs Google's own timeline

Nothing above can be instant. Realistic expectations:

- **Favicon in search results:** Google typically takes 1–4 weeks after a successful crawl to start showing a site's favicon next to results — and only after it's crawled the new `<link rel="icon">` tags and fetched the icon successfully (already confirmed reachable).
- **Re-ranking for branded terms:** depends on Google re-crawling every page with the new title tags/entity markup, which happens on its own schedule per page (higher-traffic pages get recrawled faster). Requesting indexing (Section 7, step 3) speeds this up for the specific URLs you submit, but doesn't guarantee a timeline.
- **Knowledge Panel:** these are largely automatic and depend on Google's own confidence threshold for the entity — which brings us to the next section.

## 9. The single biggest thing this report could not fix

Google's Knowledge Graph leans heavily on **`sameAs`** — corroborating links to a Wikipedia article, Wikidata entry, Crunchbase profile, or verified social accounts (X/Twitter, LinkedIn, Instagram, Facebook, YouTube) — to build confidence that "Kingdom Impact Ventures" refers to one specific, real organization rather than three ordinary English words. **This codebase has zero social media links or external profile URLs anywhere** — I checked before writing the Organization schema and deliberately left `sameAs` out rather than invent one.

This is very likely the actual root cause of "doesn't consistently return as the top branded result" — not a technical/markup gap, which this audit has now closed. **The highest-leverage next step, if you want one single recommendation, is: create (or link, if they already exist) official social profiles for Kingdom Impact Ventures, then send them over and I'll wire them into `sameAs` in about five minutes.** Everything else in this report is real and live, but it's supporting infrastructure — `sameAs` is the piece that actually tells Google's Knowledge Graph "these are all the same entity."
